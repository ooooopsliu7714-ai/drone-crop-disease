# 无人机农作物病害识别算法技术方案

> **项目**：基于无人机航拍影像的农作物病害识别与病害分布量化
> **核心命题**：用 2024–2025 年的最新方法替换原 YOLO 检测方案，交付 `POST /algo/predict` HTTP 接口
> **标签与接口契约的唯一真源**：`configs/labels.yaml`（本文所有字段名均与它逐字对齐）
> **文档状态**：技术方案 / 答辩稿底本

---

## 0. 摘要（一页话讲清方案）

我们**不再把任务建模成"一个检测器打完收工"**，而是拆成**三个各司其职的层级**：

1. **地块级初筛** —— 用自监督基础模型 **DINOv3**（Meta, 2025）的稠密特征 + 线性探测，
   先回答"**这块地有没有病、大概是哪类病**"；
2. **病斑级定位** —— 用端到端检测器 **RT-DETRv2 / RT-DETRv3**（WACV 2025）做**无 NMS** 的集合预测，
   配合**滑窗切片推理**解决大图小目标问题；
3. **像素级量化** —— 用 **SAM 2.1** 对候选框做分割，拿到**病斑真实面积**，
   进而算**发病率**与**病情指数**，产出病害分布地图与统计报表。

这三级不是简单堆叠，而是**逐级收敛**：第一级把"航拍图里病斑占比极小、直接检测召回低"的
根本矛盾用**分类先验**化解；第二级在已知有病的先验下**专注定位**，召回率与精度同时受益；
第三级把"检测框"升级为"真实面积"，让输出**从"哪里有病"变成"多严重、该不该打药"**——
这才是农户真正愿意付钱的东西。

## 1. 为什么不再用 YOLO

### 1.1 YOLO 在本任务上的四个硬伤

**（1）Anchor 与 NMS 后处理，天生不适合密集小目标**

YOLO 系列依赖预设 anchor（或 anchor-free 的中心点先验）+ 非极大值抑制作为最终决策。
这在自然图像上没问题，但航拍病斑有两个特点直接把它顶到墙角：

- **病斑极小且密集**：一张 4096×4096 正射图上，单个病斑可能只占 20×20 像素，整图缩到 640 后
  只剩 **3 个像素**——anchor 的尺度集合里根本没有这么小的先验，网络学不到。
- **NMS 会把相邻病斑互相抑制掉**。叶片上连片的病斑在 IoU 上高度重叠，
  NMS 一压，**多个真实病斑被合并成一个**，直接导致漏检；调高 NMS 阈值又会让重复框爆炸。

**（2）类别变更要重训，扩展成本高**

YOLO 的检测头输出维度与类别数**强绑定**。项目标签体系目前 15 类
（`configs/labels.yaml`：healthy + 14 种病害，覆盖水稻/小麦/玉米/马铃薯/番茄/葡萄/柑橘），
一旦要新增一种病害（比如"大豆锈病"），**必须改检测头并重新训练**，
旧权重不能复用，历史精度还可能回退。竞赛/实际推广中"新病害随时可能出现"是常态。

**（3）缺乏语义推理，只能"看到"不能"理解"**

YOLO 是纯判别式密集预测，没有全局上下文建模。而农业病害判别**高度依赖上下文**：
同样的黄色斑点，在**水稻叶片**上是稻瘟病、在**小麦叶片**上可能是条锈病；
"病斑沿叶脉条状分布"这种**形态学 + 空间关系**的语义线索，YOLO 的局部感受野抓不住。

**（4）输出的是"框"，不是"面积"**

项目要交付**病害分布地图 + 统计报表**，核心指标是**发病率**与**病情指数**：

```
病情指数 DI = Σ(病级 × 该病级代表面积) / (最高病级 × 总面积) × 100
```

`DI` 需要**面积**。检测框的矩形面积**严重高估**不规则病斑的真实面积
（病斑多为不规则斑块，框内大量像素其实是健康组织），导致病情指数系统性偏高。
**这是检测范式本身的局限，换更强的检测器也解决不了**——必须引入分割。

### 2.2 选型结论

- **检测层**：以 **RT-DETRv2** 为工程主力（生态成熟、风险低），以 **RT-DETRv3** 为冲精度方案
  （WACV 2025，训练期密集监督、推理零开销，适合竞赛叙事）。两者**无 NMS**，
  正好根治 YOLO 的第一个硬伤。
- **初筛层**：**DINOv3** 为首选（2025 最新、稠密特征强、支持多分辨率），
  **DINOv2** 作为稳妥回退（生态成熟）。二者都是**冻结 backbone + 线性探测**，正好适配 8GB 显存和小样本。
- **量化层**：**SAM 2.1** 零样本分割，避免为"像素级标注"再付一遍昂贵标注成本。
- **扩展层**：**YOLO-World / Grounding DINO** 作为新类别的零样本兜底与离线预标注工具，
  **不进入在线推理主链路**（精度与延迟都不划算）。
- **YOLO 系列**：仅作为**对照实验基线**保留，用于证明"替换是有效提升而非换汤不换药"。

### 3.2 第一级：地块级初筛

**要解决的矛盾**：航拍图上病斑像素占比常常 **< 0.1%**。让检测器在整图上直接找病斑，
等于大海捞针——**正负样本极端不平衡**，召回率极低。
人类农技员看航拍图也是先看"这片地整体发黄/有斑"，再凑近看病斑细节。
**我们把这个先验显式建模成第一级。**

**做法**：

1. 用 **DINOv3**（或 DINOv2）**冻结 backbone** 提取切片特征；
2. 在特征上训一个**线性分类头**（线性探测 / linear probing），类别即
   `configs/labels.yaml` 的 15 类（含 `healthy`）；
3. 输出"有/无病害 + 类别概率分布"，并给出**整图级别的主病害与置信度**，
   直接对应契约的顶层 `disease_name` / `disease_name_cn` / `confidence`。

**为什么用自监督基础模型而不是直接训个 CNN 分类器**：

- **标注效率**：线性探测在**每类几十~几百张**图时就能工作，而从头训 CNN 需要更多数据；
- **特征质量**：DINOv3 的**稠密特征**在无微调情况下即超越专用 SOTA（论文摘要结论），
  对"我们标注量不足"的现实约束是最优解；
- **成本**：冻结 backbone → 只有线性层要训 → **8GB 显存轻松容纳**，几分钟训完一轮。

**DINOv3 相对 DINOv2 的额外价值**：DINOv3 的 **Gram anchoring** 解决了长训练下
**稠密特征退化**的问题，且提供**分辨率外推**能力——这对"同一模型要同时处理
224 的切片和更大视野"的场景很关键。

**输出**：`{has_disease: bool, top_class, class_probs, confidence}`
→ 若判为健康或置信度过低，**短路返回**，省掉后两级算力。

### 3.3 第二级：病斑级定位

**要解决的矛盾**：小病斑在大图缩放后消失；跨切片重复框需要合并。

**做法**：

1. **切片推理**：按 `--tile 640 --overlap 128` 滑窗（`tools/tile_infer.py`），
   **绝不做整图缩放**——整图 4096→640 会把 20px 病斑压成 3px，信息不可逆丢失；
2. **逐片 RT-DETR 推理**：端到端集合预测，**天然无 NMS**，
   从根上避免"相邻病斑互相抑制"；
3. **映射回原图坐标 + class-wise NMS**：切片局部坐标加上切片偏移得到全局坐标，
   再用**按类别分组的贪心 NMS** 合并重叠区的重复检测。
   *为什么不直接全局 NMS*：不同类别的框即使重叠也**不应互相抑制**——
   同一位置同时存在两种病害在农业上是可能的；且类别混淆不该被 NMS 掩盖。
   另外加一条跨类规则：同位置若一个判 `healthy`、一个判病害，**保留病害**
   （病虫害防治以病害为准，漏报代价 >> 误报代价）。

**为什么 RT-DETR 系列比 YOLO 更适合**：

| 维度 | YOLO | RT-DETR v2/v3 |
| --- | --- | --- |
| 后处理 | anchor + NMS，**密集小目标易被抑制** | **无 NMS**，集合预测直接输出最终框 |
| 全局建模 | 局部感受野为主 | Transformer 编码器-解码器，**全局上下文** |
| 速度 | 快 | RT-DETR-R50 已 108 FPS@T4，**实时性不输** |
| 训练监督 | 密集监督，收敛快 | v3 用**分层密集正监督**补上这块短板 |

**RT-DETRv3 的关键工程优势**：其全部改进模块（CNN 辅助分支、自注意力扰动、
共享权重解码器分支）**只在训练期存在**，推理结构不变——
**精度白拿，延迟不涨**。这对答辩极有说服力："我们拿到了 +1.6 AP，但线上延迟一分没变"。

### 3.4 第三级：像素级量化

**要解决的矛盾**：检测框是矩形，**严重高估**不规则病斑面积，使病情指数系统性偏高。

**做法**：把第二级输出的每个候选框作为 **box prompt** 送进 **SAM 2.1**，
得到病斑的**像素级掩码**，统计真实面积后计算农业指标：

```
发病率   = Σ(病斑像素面积) / 地块(图)总面积 × 100%
病情指数 DI = Σ(病级 × 该病级代表面积) / (最高病级 × 总面积) × 100
```

其中病级权重**严格取自 `configs/labels.yaml` 的 `severity_index`**：

| severity | 中文 | severity_index | 对应国标病级 |
| --- | --- | ---: | --- |
| `healthy` | 健康 | 0 | 0 |
| `light` | 轻度 | 1 | 1 |
| `moderate` | 中度 | 2 | 2 |
| `severe` | 重度 | 3 | 3 及以上 |

> 病情指数的**分级加权思路**与我国农业测报规范一致
> （例如 **GB/T 15795—2011《小麦条锈病测报技术规范》** 中的发生程度分级）。
> 注意：`DI` 的具体分母口径（按面积还是按株数）**各病害国标略有差异**，
> 若答辩需要引用某一具体作物的国标公式，**请按该作物的现行国标核实后引用**，
> 不要泛化为"统一国标公式"。

**为什么用 SAM 2.1 而不是训一个分割网络**：

- **零标注成本**：像素级标注极其昂贵，SAM 2.1 **零样本**即可分割，省掉整条标注流水线；
- **性能**：SAM 2 论文报告图像分割上比初代 SAM **更准且快 6×**；
- **风险**：对**低对比度、极细小**的病斑，SAM 2.1 边界可能偏粗，
  → 需做**面积校正**（如按验证集拟合一个线性校正系数），
  或对关键类别改用**轻量分割头**（用少量像素标注监督）作为备选。

**输出**：`statistics.diseased_ratio`（发病率）、`statistics.disease_index`（病情指数）、
`statistics.severity_ratio`（各严重度占比）、`statistics.class_ratio`（各类别占比）
——字段名与 `src/api/schema.py` 的 `Statistics` 模型一致。

### 3.5 「AI 初筛 + 农技员复核」如何落到接口上

**这不仅是产品设计，更是我们解决"标注量不足"的技术手段。**

**（1）触发复核的条件**（写进服务端逻辑，字段体现在响应中）：

| 条件 | 阈值（示例，需按验证集调） | 动作 |
| --- | --- | --- |
| 主病害置信度低 | `confidence < 0.6` | 进复核队列 |
| 第一级与第二级结论不一致 | 初筛类别 ∉ 检测类别集合 | 进复核队列 |
| 单图出现类别冲突 | 同位置 IoU>0.85 但类别不同 | 进复核队列 |
| 新类别 / 分布外 | 特征距离超阈值，或 YOLO-World 零样本命中未训练类 | 进复核队列 |
| 严重度高且面积大 | `severity == severe` 且 `disease_index` 高 | **优先复核**（救治窗口紧） |

**（2）接口层的落地方式**：

- 响应仍**严格返回契约字段**（`code` / `message` / `image_id` / `disease_name` /
  `disease_name_cn` / `confidence` / `severity` / `boxes` / `processing_time`），
  **队友的 Apifox 解析不受影响**；
- 复核需求通过**扩展字段**表达（增量、不破坏兼容）：
  `statistics`（量化结果）、`model_version`（模型标识，便于 A/B 与复现）、
  `backend`（实际推理后端）。
  若需显式复核标记，**建议新增扩展字段**（如 `needs_review: bool`、
  `review_reasons: list[str]`）——**但这属于契约变更，必须先同步 Apifox 与队友确认**，
  不可单方面加改。

**（3）复核结果如何回流（半监督闭环）**：

```
农技员复核裁决
      │
      ├─► 高置信度但被纠正的样本 ──► 直接进训练集（强监督）
      │
      └─► 未复核的推理结果 ──► 伪标签 + 置信度加权
                                    │
                                    ▼
                      半监督训练（Soft Teacher 式软加权 / Unbiased Teacher 式师生互训）
                                    │
                                    ▼
                              模型迭代 → 复核量下降 → 闭环收敛
```

**参考方法**：
- **Soft Teacher**（ICCV 2021, arXiv:2106.09018）：用教师网络的分类分数**加权**无标注框的分类损失，
  并用 box jittering 挑可靠伪框回归；
- **Unbiased Teacher**（ICLR 2021, arXiv:2102.09480）：处理伪标签的**类别偏置**，
  用类别平衡损失压制过度自信的伪标签。

**业务价值**：这条闭环让"人工复核"从**纯成本**变成**数据资产**——
复核得越多，模型越准，需要复核的越少。答辩时这是"完成度"与"可持续性"的强证据。

## 4. 训练策略

### 4.1 小样本冷启动：三阶段递进

面对"标注数据少"的现实，**不要一上来就端到端全量微调**。

| 阶段 | 做法 | 训什么 | 数据量需求 | 8GB 可行性 |
| --- | --- | --- | --- | --- |
| **① 线性探测** | 冻结 DINOv3/DINOv2 backbone，只训线性分类头 | 线性层 | 每类几十张即可 | ✅ 极轻松 |
| **② LoRA 微调** | 在 backbone 的注意力层注入低秩矩阵（**LoRA**, ICLR 2022, arXiv:2106.09685），冻结原权重 | 秩分解矩阵，**<1% 参数** | 每类数百张 | ✅ 显存增量极小 |
| **③ 全量 / 部分解冻** | 解冻后若干 stage 做精调 | 部分 backbone + head | 每类上千张 | ⚠️ 需 batch 2–4 + AMP |

**为什么用 LoRA**：LoRA 论文的核心结论是"冻结预训练权重 + 注入秩分解矩阵"可将
**可训练参数减少 1 万倍、显存需求降低 3 倍**，且质量与全量微调相当甚至更好。
对 8GB 显存 + 小样本的场景，这是**性价比最高的适配方式**。
（LoRA 原论文面向 LLM，迁移到 ViT/检测器是社区的成熟实践，
**具体在本项目的增益需用消融实验实测**，不要直接引用 NLP 结论。）

### 4.2 类别不均衡

`configs/labels.yaml` 的 15 类在真实数据上**必然极度不均**：
常见病害（稻瘟病、小麦条锈病）可能有上万框，冷门病害（柑橘黄龙病）可能只有几百框。

| 手段 | 具体做法 | 依据 |
| --- | --- | --- |
| **Copy-Paste 增强** | 把稀有类别的病斑**抠出来随机粘贴**到其他图上。论文证明"简单随机粘贴"就足够有效，且在 LVIS **稀有类别**上比 2020 挑战赛冠军高 +3.6 mask AP | Ghiasi et al., CVPR 2021, arXiv:2012.07177 |
| **Focal Loss** | 重塑交叉熵，**降低易分样本权重**，聚焦难例，专治正负样本极端不平衡 | Lin et al., ICCV 2017, arXiv:1708.02002 |
| **Varifocal Loss** | 用 **IoU-aware 分类分数**联合表示"有无目标 + 定位准不准"，排序更可靠 | Zhang et al., CVPR 2021 Oral, arXiv:2008.13367 |
| **重采样 / 类别权重** | 按类别频率倒数加权采样；或对长尾类提高 loss 权重 | 常规实践 |
| **评测看每类指标** | 不只报 mAP，**必须报每类 P/R/F1**，否则长尾问题被平均值掩盖 | 见 §5 |

### 4.3 小目标（本项目的头号难题）

| 手段 | 说明 |
| --- | --- |
| **切片训练** | 训练时也从大图切 640×640 片，**让网络在小目标原生尺度上学**，而非学缩放后的退化特征。这是与推理侧 `tools/tile_infer.py` **对齐**的关键——**训练与推理的尺度分布必须一致** |
| **更高输入分辨率** | 640 → 1024/1280。代价是显存约按面积平方增长，8GB 下需配合 batch=2 + AMP |
| **多尺度训练** | 随机缩放（如 480–1280），提升尺度鲁棒性 |
| **FPN / 多尺度特征融合** | RT-DETR 的混合编码器已在做跨尺度融合；确保小目标层（P2/stride-4）被纳入 |
| **标注质检前置** | **用 `tools/vis_labels.py` 先查一遍**：如果大量框在原图缩到 640 后短边只剩 4px，那**再强的模型也学不到**——必须回标注环节解决（重标或提高分辨率） |

> **工程经验**：小目标问题上，**"数据/尺度对齐"的收益往往大于"换模型"**。
> 建议先把 `tools/vis_labels.py` 的"小目标占比"这一项压到 <30%，再谈模型选型。

### 4.4 域适应（不同无人机 / 高度 / 光照）

真实推广中，训练数据可能来自 A 型号无人机、上午顺光，而部署时是 B 型号、黄昏逆光。
**域偏移会让精度断崖式下跌**。

| 手段 | 强度 | 说明 |
| --- | --- | --- |
| **颜色增强** | 低 | 亮度/对比度/饱和度抖动、HSV 偏移、随机 gamma。**成本最低、必做** |
| **天气/光照模拟** | 低 | 加雾、加雨、加阴影、模拟逆光 |
| **几何增强** | 低 | 旋转（航拍可 90° 倍数旋转，符合物理）、缩放、翻转、mosaic |
| **风格迁移（可选）** | 中 | 用 **FDA（Fourier Domain Adaptation, CVPR 2020, arXiv:2004.05498）** 交换源域与目标域的**低频频谱**做无监督域对齐——**无需训练、只需一次 FFT**，实现成本极低但效果显著 |
| **域随机化** | 中 | 训练时大幅随机化成像参数，逼模型学域不变特征 |
| **伪标签自训练** | 高 | 在目标域上跑推理 → 挑高置信度伪标签 → 微调。与 §3.5 的复核闭环**复用同一套基础设施** |

### 4.5 伪标签半监督闭环

结合 §3.5 的农技员复核，形成完整闭环：

1. 在未标注/新域数据上推理；
2. 用**置信度阈值 + 一致性检查**（如多尺度/翻转 TTA 结果一致）筛出可靠伪标签；
3. 用 **Soft Teacher** 式软加权（按教师分数加权损失）或 **Unbiased Teacher** 式类别平衡
   压制伪标签偏置；
4. 混合有标注 + 伪标注数据训练，迭代 2–3 轮。

**注意**：伪标签会**放大模型已有的错误**（确认偏误）。
务必保留 held-out 验证集，**每轮都验证**，一旦验证集下降就回退。

## 5. 评估方案与指标

### 5.1 检测指标（对齐 COCO 口径）

| 指标 | 说明 | 为什么报它 |
| --- | --- | --- |
| **mAP@0.5** | IoU 阈值 0.5 下的平均精度 | 行业最常引用的单值指标 |
| **mAP@0.5:0.95** | IoU 0.5→0.95 步长 0.05 平均 | **更严格**，反映定位精度；评审更认可 |
| **每类 P / R / F1** | 逐类别精确率、召回率、F1 | 暴露长尾类别的真实水平，防止被平均值掩盖 |
| **每类 AP@0.5** | 逐类别 AP | 定位最弱类别，指导补数据 |

> **口径声明**：mAP **必须用官方 `pycocotools` 评测器**计算。自实现的 mAP
> 在插值方式、忽略区域处理上与官方有差异，**评审可能不认可**。
> 当前环境 `pycocotools` 未装，**这是评估阶段的阻塞项，需优先安装**（见 `REQUIREMENTS.md` §2.3）。

### 5.2 农业指标（这是我们的差异化）

| 指标 | 定义 | 验证方式 |
| --- | --- | --- |
| **发病率** | `Σ病斑面积 / 总面积` | 与人工实测（或高精度人工勾画）对比，报 **MAE / 相对误差** |
| **病情指数 DI** | `Σ(病级×面积)/(最高病级×总面积)×100` | 与农技员按国标分级的人工评分对比，报 **MAE 与等级一致率** |
| **严重度分级准确率** | 预测 `severity` 与人工分级的**四分类一致率**（healthy/light/moderate/severe） | 混淆矩阵 + 准确率 |
| **误报率（False Alarm Rate）** | `FP / (FP + TN)`，即"把健康判成有病的比例" | **单独重点报告** |

> **为什么必须单独报误报率**：这是**农户最关心的指标**。漏报（FN）会让农户错过防治窗口；
> 但**误报（FP）会让农户白打一遍药**——直接损失真金白银，还会**摧毁对系统的信任**。
> 农户宁可系统说"我没看出来"，也不要系统"吓唬他"。
> 答辩时主动把误报率单列，体现**对农业场景的真实理解**，这是加分项。

### 5.3 对照实验设计

要证明"换方法有用"，必须有**受控对比**：

| 实验组 | 配置 | 目的 |
| --- | --- | --- |
| **A. Baseline** | YOLOv8（或 YOLO11），640 输入，整图训练/推理 | 复现原方案，确立参照系 |
| **B. 单级替换** | RT-DETRv2-R18，640 输入，**其余与 A 完全一致** | 隔离"检测器替换"的收益 |
| **C. 单级替换（精度版）** | RT-DETRv3-R18，640，其余同 A | 隔离"v3 密集监督"的增量收益 |
| **D. 加切片推理** | RT-DETRv2 + `tile 640/overlap 128` 切片推理 | 隔离"大图小目标处理"的收益 |
| **E. 加初筛** | DINOv3 线性探测 + RT-DETRv2 | 隔离"分类先验"对召回的影响 |
| **F. 完整三级流水线** | 初筛 + RT-DETRv2/v3 切片 + SAM 2.1 量化 | **最终方案** |

**消融要点**：

- **A vs B vs C**：检测器替换值不值？v3 比 v2 多的那 +1.6 AP 在**我们的数据**上成立吗？
- **B vs D**：切片推理对小目标的召回提升有多大？（预期**这是最大的单项增益**）
- **D vs E**：初筛带来的召回提升 vs 引入的额外延迟，划算吗？
- **E vs F**：分割量化对**病情指数 MAE** 的改善（检测框 vs 真实面积）
- **A vs F**：端到端总结论，**同时报告精度提升与延迟代价**

**必须同时报告**：每组的 mAP@0.5、mAP@0.5:0.95、误报率、**单张延迟（ms）**、显存占用。
**只报精度不报延迟是对评审的不负责**——生产环境里延迟和精度同等重要。

### 5.4 统计显著性

小数据集上的 mAP 差异可能只是**随机波动**。建议：

- 用 **3–5 个不同随机种子**各跑一遍，报**均值 ± 标准差**；
- 若两组差异小于合并标准差，**不要声称"我们的方法更好"**，应说明"差异在噪声范围内，需更多数据验证"。
  这种**诚实的表述反而会提升评审对技术判断力的评价**。

## 6. 工程落地

### 6.1 FastAPI 接口

**契约（唯一真源 `configs/labels.yaml`，禁止改名）**：

```
POST /algo/predict

请求（二选一）：
  A. JSON:                  {"image_id": "abc123"}
  B. multipart/form-data:   file=<图片文件>

响应顶层：
  code: int                200 成功
  message: str             提示信息
  image_id: str
  disease_name: str        主病害英文标识（取置信度最高的框/分类结果）
  disease_name_cn: str     主病害中文名
  confidence: float        主病害置信度 0~1，保留 4 位小数
  severity: str            healthy | light | moderate | severe
  boxes: list              识别框
  processing_time: float   服务端处理耗时（秒）

boxes[] 元素：
  disease_name, disease_name_cn, confidence, severity, class_id,
  x, y, w, h          # 归一化坐标 0~1（相对原图），小程序按百分比画框
  x1, y1, x2, y2      # 像素坐标，后端画热力图
  兼容字段：label / score / bbox（冗余返回，主字段始终是 disease_name / confidence / boxes）

扩展字段（增量，不影响队友既有解析）：
  statistics（发病率/病情指数/严重度占比/类别占比）、model_version、backend
```

**工程要求**：

- **`boxes` 与顶层 `severity` 的关系**：顶层 `severity` 是**整图/整地块**的严重度
  （由第三级量化的病情指数分级得出），`boxes[].severity` 是**单个病斑**的严重度。
  两者含义不同，**不要混用**。
- **无病时（本仓库 `src/api/service.py` 的真实行为，已由 `tests/test_contract.py` 锁定）**：
  `disease_name = "healthy"`、`disease_name_cn = "健康"`、`severity = "healthy"`、`code` 仍为 `200`
  （**"没查出病"是正常业务结果，不是错误**）。
  `boxes` 的处理分两种后端，**前端要按这个约定解析**：
  - **分类后端（DINOv2/v3 线性头）→ `boxes` 为空列表**，`confidence` 是"判为健康"的置信度，
    即前端应理解为"健康，把握 92%"而不是"病害置信度 0.92"；
  - **检测/基线后端 → 返回一个覆盖全图的框**（`disease_name="healthy"`，坐标为 `[0,0,W,H]`），
    好处是前端画框逻辑不需要为"无框"写分支，热力图也能拿到整图范围。

  > 判据统一用 `disease_name == "healthy"`，**不要**用 `len(boxes) == 0` 判断是否健康，
  > 否则切换后端时前端会出现行为差异。这一条已写进 `tests/test_contract.py`
  > （健康图 `disease_name == "healthy"` 且 `severity == "healthy"` 恒成立）。
- **主病害置信度与整图置信度**：顶层 `confidence` 是主病害（置信度最高框/分类结果）的置信度；
  `advice.need_expert_review = true` 表示它低于 0.6，应进农技员复核队列。
- **`processing_time`** 必须真实测量（服务端 `time.perf_counter()` 差值），
  **不要伪造或返回固定值**——这是答辩性能证据的一部分。
- **坐标裁剪**：`x1/y1/x2/y2` 必须裁到 `[0, image_w/h]`，避免前端画框飞出画布。

### 6.2 ONNX 导出与部署

| 路线 | 场景 | 说明 |
| --- | --- | --- |
| **PyTorch 原生（推荐起步）** | 服务端 GPU | 零转换成本，`torch.compile` 可再提速；**避免 CUDA/cuDNN 版本地狱** |
| **ONNX + onnxruntime** | 服务端 CPU / 无 GPU 环境 | 导出后跨平台，CPU 上常比 PyTorch 快 1.5–2×；依赖 `onnx` + `onnxruntime` |
| **ONNX + onnxruntime-gpu** | 服务端 GPU | 需 CUDA/cuDNN 版本严格匹配，**版本矩阵需核实**，风险较高 |
| **量化（INT8）** | 端侧 / 小程序 | 体积与延迟大幅下降，精度略降，需实测验收 |

**导出注意事项（RT-DETR 特有问题）**：

- RT-DETR 的**后处理（top-k 查询解码、框反归一化）需要一并导出或单独实现**，
  否则 ONNX 只输出原始查询，前端无法直接用；
- **动态 batch / 动态分辨率**导出需 `dynamic_axes` 显式声明；
- **务必导出后做数值对齐验证**：同一张图，PyTorch 与 ONNX 的输出框
  **IoU 应 >0.99**，否则说明导出有精度损失。

**降级容错**：服务端应能探测 `onnxruntime` 是否可用、CUDA 是否可用，
**自动选择后端并在响应 `backend` 字段中如实报告**（如 `pytorch-cuda` / `onnxruntime-cpu`）。
这样"环境没配好"不会导致服务起不来，只是变慢。

### 6.3 推理耗时预算（验收线）

| 场景 | 目标 | 说明 |
| --- | --- | --- |
| 单张 640 图 · **CPU** | **≤ 1.5 s** | 无 GPU 的演示/联调环境兜底 |
| 单张 640 图 · **GPU** | **≤ 200 ms** | RT-DETR 实时性完全够（R50 在 T4 上 108 FPS） |
| 大图切片（4096×4096） | **≤ 30 s** | 9–49 片串行；可用 batch 化切片推理再压缩 |
| 接口 p95 | **≤ 2 × 均值** | 稳定性指标，抖动大说明有资源竞争 |

**用 `tools/bench_latency.py` 产出实测证据**（含 p50/p95/QPS/成功率/显存内存），
报告可直接贴进答辩 PPT。**注意区分两个耗时**：

- **客户端耗时**：含网络 + 排队 + 序列化 → 决定用户体验；
- **服务端 `processing_time`**：只含模型推理 → 决定算力需求。

**两者差值**是网络与调度开销，**QPS 上不去时优先看它**。

**大图切片耗时优化方向**（若 30s 不达标）：

1. **batch 化切片**：一次把 8/16 片拼成 batch 送 GPU，吞吐提升数倍；
2. **跳过低风险片**：用第一级初筛给每片打分，**只对可能有病的片做检测**——
   这是三级流水线带来的**结构性加速**，是相对"单检测器"的额外优势；
3. **蒸馏到小模型**：用 RT-DETR-l 蒸馏 RT-DETR-s，精度略降、速度快一倍。

### 6.4 与小程序端 / Java 后端的联调

| 环节 | 方式 | 注意事项 |
| --- | --- | --- |
| **联调契约** | **Apifox** 作为唯一契约源，算法侧以 `configs/labels.yaml` 末尾注释为准 | **任何字段改名都必须先同步 Apifox**，否则联调必挂 |
| **Mock 先行** | Apifox Mock 先返回假数据，前端与 Java 后端**不等算法就位即可并行开发** | 降低关键路径依赖 |
| **图片传递** | 方式 A：小程序/Java 先上传图片拿到 `image_id`，再传 `image_id` 给算法服务<br>方式 B：直接把文件 multipart 传给算法服务 | **方式 A 更适合生产**：图片存储与算法解耦，算法服务无状态、易扩缩容 |
| **坐标使用** | 小程序用 `x/y/w/h`（归一化，按百分比画框，**天然适配不同分辨率**）<br>Java 后端用 `x1/y1/x2/y2`（像素，画热力图/做统计） | **两套坐标同时返回**正是为此，前端不必自己换算 |
| **热力图与报表** | 后端拿 `boxes` 调 `tools/make_heatmap.py` 生成分布图与网格 CSV；<br>评估报告用 `tools/report_export.py` 导出 Excel + Markdown | 复用同一套字段，无需二次开发 |
| **错误约定** | 成功 `code=200`；参数错误/图片不存在等用非 200 + 中文 `message` | **不要用 HTTP 500 表达业务错误**，前端需能区分 |
| **性能验收** | 用 `tools/bench_latency.py` 对真实接口压测，**验收数据写进对接文档** | 避免"我这很快"vs"我这一直转圈"的扯皮 |

## 7. 风险与备选方案

| 风险 | 影响 | 概率 | 应对 / 备选方案 |
| --- | --- | --- | --- |
| **8GB 显存不足** | 训不了大模型 | 高 | ① 640 输入 + batch 2–4 + AMP + 冻结 backbone（**默认配置**）；② 换 R18/ViT-S 小档模型；③ 梯度累积换等效 batch；④ **云 GPU 租用**（AutoDL/阿里云）做最终训练，本地只做调试 |
| **标注量不够** | 精度上不去 | 高 | ① DINOv3/ViT **冻结 backbone + 线性探测**（少样本友好）；② **Grounding DINO 零样本预标注** + 人工修正，把标注成本降一个数量级；③ Copy-Paste 造稀有类样本；④ **半监督伪标签闭环**（§3.5）；⑤ **迁移学习**：先用 PlantVillage 等公开数据集预训练 |
| **类别新增** | 需重训，旧权重失效 | 中 | ① **YOLO-World 零样本**先兜底（新类无标注也能出结果）；② 只重训检测头 + LoRA，**不重训 backbone**；③ 类增量学习（后续扩展方向）。**注意**：新增类别会改变 `class_id` 映射，`configs/labels.yaml` 明确警告"修改顺序会使已训练权重失效"，**必须走版本管理** |
| **无人机数据隐私** | 合规风险 | 中 | ① 农田影像含**地理位置**，属敏感信息，**存储前剥离 EXIF GPS**；② 数据本地化部署（**不上传公有云**）；③ 训练数据去标识化；④ 与甲方签数据处理协议；⑤ 若用公有云训练，**先脱敏再做** |
| **SAM 2.1 分割边界偏粗** | 病情指数偏差 | 中 | ① 按验证集拟合**面积校正系数**；② 对关键类别改用**轻量分割头**（少量像素标注监督）；③ 用检测框面积与掩码面积做**一致性校验**，差异过大则降级用框面积并标记低可信 |
| **域偏移（换无人机/光照）** | 部署精度骤降 | 高 | 见 §4.4：颜色增强（必做）+ **FDA 频谱域适应**（无需训练）+ 目标域伪标签微调 |
| **RT-DETRv3 权重/生态不足** | 无法复现 | 中 | ① 以 **RT-DETRv2 为工程主力**保交付；② v3 作为**精度冲刺项**，仅在其权重与代码验证可用后接入；③ 若 v3 不可用，用 v2 + 更强数据增强/更长训练弥补 |
| **接口字段被单方面改动** | 联调失败 | 中 | ① 以 `configs/labels.yaml` 为唯一真源，**改字段必须先改 Apifox**；② 扩展字段采用**纯增量**策略，新增不删改；③ 保留 `label`/`score`/`bbox` 兼容字段 |
| **评估器缺失导致 mAP 不可信** | 评审不认可 | 中 | 优先安装 `pycocotools`；若 Windows 编译失败，用 `pycocotools-windows` 或自实现并在报告中**明确标注口径差异** |
| **答辩时间紧，方案讲不清** | 失分 | 中 | 用本文 §3.1 的 ASCII 流程图 + §5.3 的对照实验表；**主打"三级流水线"一个记忆点**，不贪多 |
